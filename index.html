03

Publium

2026.072인 팀, 8일 개발백엔드, 검색 Agent, 배포

모아 둔 PubMed 논문에서 질문에 맞는 내용을 검색해 답하고, 근거 논문의 PMID를 함께 보여 주는 서비스입니다.

FastAPI 백엔드와 PubMed 수집, 논문 검색 도구를 연결한 Agent를 맡았습니다. 답변에 사용한 PMID를 표시하도록 했습니다.

논문을 수집하는 동안 다른 요청까지 기다리는 문제가 있었습니다. 동기 호출을 별도 스레드로 옮기고, 수집 중에도 상태 확인 요청이 응답하는지 확인했습니다.

이후 pgvector와 그래프 RAG를 이용한 리뉴얼은 팀원이 맡았습니다.

서비스 GitHub 코드

Python, FastAPI, LangChain, Supabase Postgres, Render

직접 구현한 것

FastAPI 백엔드와 데이터 계층
PubMed E-utilities 수집, 논문 목록과 채팅 기록 저장, 삭제 API. Supabase Postgres 연결과 구글 로그인.
툴콜링 에이전트
LangChain create_agent에 수집 논문용 검색 툴을 붙였습니다. 근거가 필요한 질문은 검색부터 하도록 프롬프트로 지시하며, 사용한 PMID를 표시합니다.
서버 측 가드
진단, 처방, 복용량 같은 의료 조언은 정규식으로 요청을 차단해 LLM에 보내지 않고, 고정 안내문으로 답합니다.
스트리밍과 응답성
토큰 단위로 스트리밍하며, 동기 DB와 PubMed 호출은 스레드로 분리해 이벤트 루프가 멈추지 않게 했습니다.
배포
Supabase Postgres 기반으로 Render에 무료 배포했고, 이후 리뉴얼(pgvector, 그래프 RAG)은 팀원이 담당합니다.

기술 선택

답변 구조
선택

LangChain 툴콜링 에이전트. 모델이 검색 여부와 검색어를 정함

대안

검색 결과를 프롬프트에 붙이는 고정 파이프라인

이유

후속 질문이면 대화 기록의 PMID나 키워드로 다시 검색해야 했습니다. 검색어를 코드로 정하지 않아도 되는 대신, 찾지 못하면 없다고 답하도록 프롬프트로 순서를 잡았습니다.

블로킹 I/O
선택

asyncio.to_thread로 동기 호출만 스레드로 분리

대안

DB 드라이버와 HTTP 클라이언트를 전부 비동기로 교체

이유

기존 동기 코드가 이미 동작하고 있었고 기간이 짧았습니다. 문제는 async 핸들러 안의 동기 호출이었으므로 호출 지점만 넘기는 쪽이 변경 범위가 가장 작았습니다.

의료 조언 차단
선택

서버 정규식 가드와 고정 응답

대안

시스템 프롬프트로만 금지

이유

프롬프트 지시는 우회될 수 있고, 차단할 때 반환하는 문구는 항상 같아야 했습니다. LLM 호출 전에 서버에서 끊으면 비용도 들지 않습니다.

트러블슈팅

논문 수집 요청이 길어지면 서버 전체가 응답하지 않았습니다.

  1. 증상PubMed 수집 요청 중에는 다른 요청도 상태 확인도 모두 기다려야 했습니다.
  2. 원인동기 PubMed, DB 호출이 async def 핸들러 안에서 그대로 실행되면서 이벤트 루프 전체를 막았습니다.
  3. 조치동기 호출을 asyncio.to_thread로 스레드풀에 넘기고, 동시 수집은 세마포어로 2개까지 제한했습니다. 수집 중 /health 응답을 확인하는 테스트도 추가했습니다.
  4. 다시 한다면처음부터 async 드라이버를 쓰거나, 동기 라이브러리를 쓰는 핸들러는 def로 선언해 FastAPI가 스레드풀에서 실행하게 하겠습니다.

버리미 (Beorimi)

2026.083인 팀, 28시간 MVP팀장, 백엔드와 분석 워커

버릴 물건을 찍으면 품목과 예상 수수료를 보여주고, 신고 페이지로 연결합니다.

사진 분석을 워커에서 처리하고, 화면에서 진행 상태를 확인할 수 있게 만들었습니다.

모델이 찾은 품목과 규격은 강남구 공식 카탈로그에 맞춰 수수료를 계산합니다. 잘못 인식한 항목은 사용자가 고칠 수 있습니다.

서비스 GitHub 코드

Next.js, Supabase, OpenAI

사진 한 장에서 예상 수수료까지

사진 속 여러 폐기물을 품목별로 나눠 행정 기준과 연결했습니다. VLM의 추정값을 그대로 보여 주지 않도록 고정 스키마로 받은 값을 강남구 공식 수수료 카탈로그와 다시 매칭했습니다.

  1. 사진 촬영여러 품목을 한 프레임에 담아 그대로 촬영합니다.
  2. 다중 품목 인식의자, 서랍장 등을 구분해 각각의 규격을 추정합니다.
  3. 사용자 확인잘못 인식된 품목은 사용자가 직접 고치도록 설계했습니다.
  4. 수수료 산출강남구 수수료 기준표에 맞춰 품목별 금액과 합계를 안내합니다.

비동기 분석 흐름

  1. 사진 업로드
  2. 작업 등록, 202 반환
  3. 워커의 VLM 분석
  4. 출력 검증, 수수료 매칭
  5. 상태와 결과 조회

기술 선택

인프라
선택

Supabase 하나로 Auth, Storage, Postgres, 큐, 워커까지

대안

AWS Cognito, S3, DynamoDB, SQS, Lambda 조합 (첫날 설계)

이유

28시간 안에 구현과 배포를 마치려고, 사용해 본 Supabase로 전환했습니다. SQS 대신 Postgres 행과 pg_net으로 큐를 구현하면서 인프라 설정 범위도 줄였습니다.

분석 처리
선택

202 반환 후 Postgres 큐와 워커, 브라우저는 폴링

대안

요청 핸들러에서 VLM 응답까지 동기로 대기

이유

요청이 서버에 닿았는지, VLM이 실패했는지 구분해야 했지만 동기로 연결한 화면에는 로딩만 보였습니다. 작업을 행으로 남기면 상태와 오류 메시지가 남아 어느 단계에서 멈췄는지 확인할 수 있습니다.

VLM 출력
선택

Structured Outputs strict JSON Schema, guardrail 필드 포함

대안

자유 텍스트 응답을 서버에서 파싱

이유

수수료 매칭에 필요한 입력을 strict JSON Schema로 고정했습니다. 모델이 반환한 guardrail 필드에 프롬프트 인젝션 신호가 있으면 결과를 저장하지 않고 실패 처리합니다.

그 밖의 개인 프로젝트 (저장소 비공개)

  • cogito반복 작업을 에이전트에 맡길지 코드로 고정할지, 개인 AI 에이전트로 실험합니다.
